# Neural Service Mesh (NSM)

منصة ذكاء اصطناعي عربية متخصصة بالمعرفة الإسلامية، مبنية بـ Python/Streamlit،
تجمع بين قاعدة معرفة رمزية (CKG) وشبكات عصبية مخصّصة مبنية من الصفر (بدون
PyTorch/TensorFlow — numpy فقط للمكوّن المعرفي الأساسي؛ `torch` مستخدَم
بمكوّنات صوت/فيديو منفصلة، انظر `requirements.txt`)، بالإضافة لمنظومة وكلاء
ذكاء اصطناعي متعددة الفئات مبنية فوق نفس البنية التحتية.

## 📋 نظرة سريعة (لمن يفحص المشروع لأول مرة)

| | |
|---|---|
| **النوع** | تطبيق Streamlit وحيد (monolith) + وحدات Python مساعدة (`ai/`, `knowledge/`, `core/`, إلخ) |
| **حجم الواجهة الرئيسية** | `streamlit_app.py` — ~9,800 سطر (لسه ملف واحد، مرشّح للتقسيم) |
| **اللغة الأساسية للواجهة** | العربية بالكامل |
| **الأصل الأكثر تفرّداً** | قاعدة المعرفة المعرفية (CKG): ~7,300 مفهوم، ~19,000 علاقة، مستخرجة من القرآن الكريم |
| **الاعتماد على خدمات خارجية** | اختياري بالكامل — يعمل بدون أي مفتاح API عبر احتياطي محلي (`NSM/LLMFallback` + CKG synthesis) |
| **قاعدة بيانات** | SQLite محلية (بدون خادم قاعدة بيانات خارجي) |
| **حالة النشر** | منشور فعلياً على Streamlit Community Cloud |
| **حالة الاختبارات الآلية** | جزئية — ملفات `test_*.py` متفرقة بدون تغطية كاملة، لكن CI فعّال فعلياً (`.github/workflows/tests.yml` يشغّل pytest + py_compile على كل push/PR، بالإضافة لـ`contrast-check.yml`) |

## نظرة عامة على المعمارية

النظام **ليس نموذج لغة واحد ضخم** — هو **pipeline** بيجمع بين مكونات متخصصة:

```
سؤال المستخدم
      │
      ▼
┌─────────────────────────────┐
│  Concept Knowledge Graph     │  قاعدة معرفة رمزية: ~7,300 مفهوم،
│  (knowledge/cognitive_graph  │  ~19,000 علاقة، مستخرجة من القرآن الكريم
│   .json)                     │
└──────────┬────────────────────┘
           │ يحوّل السؤال إلى متجه 784 بُعد
           ▼
┌─────────────────────────────┐
│  NeuralCore (~640K باراميتر) │  مصنّف: مدخل 784 → مخرج 4 أوزان قرار
│  ai/neural_core.py            │  (دلالي/تسجيل/ذاكرة/طوبولوجي)
└──────────┬────────────────────┘
           │ يوجّه ترتيب المفاهيم المطابقة
           ▼
┌─────────────────────────────┐
│  ArabicTransformer (~40M)    │  يعزّز الترتيب دلالياً عبر مقارنة
│  ai/arabic_transformer.py     │  hash IDs (بدون توليد نص حر —
│                                │  tokenizer لا يخزّن مفردات، انظر أدناه)
└──────────┬────────────────────┘
           │
           ▼
┌─────────────────────────────┐
│  قوالب نصية                  │  تبني الإجابة النهائية المقروءة
│  (_build_answer_text)         │  من المفاهيم المرتّبة
└─────────────────────────────┘
```

الملف المحوري: **`ai/reasoning_pipeline.py`** (كلاس `ReasoningPipeline`) — هو
اللي بيربط كل المكونات دي مع بعض، وهو المسار الوحيد المتصل فعلياً بالواجهة
الحية (`streamlit_app.py`).

## نقطة معمارية مهمة: لماذا الشبكات لا تولّد نص حر؟

`ArabicTransformer` بيستخدم **HashTokenizer** — محوّل كلمات إلى أرقام عبر
دالة hash (FNV-1a) **بدون أي قاموس مخزّن**. هذا قرار متعمّد: الأوزان
المحفوظة (`models/*.npy`) **لا تحتوي على أي بيانات خام أو مفردات**، فقط
أرقام (parameters) لا تحمل معنى بدون الكود نفسه.

**الأثر العملي:** الشبكة تقدر "تفهم" (تقارن hash IDs، تعزّز ترتيب) لكن
**مش تقدر تطلّع نص عربي حر مقروء** (مفيش `decode()`). النص النهائي دايمًا
بييجي من القوالب + بيانات CKG الحقيقية — ده اللي بيضمن الدقة (مفيش
هلوسة/اختلاق حقائق).

## المكونات الرئيسية

| المكون | الحجم | الحالة | الملف |
|---|---|---|---|
| CKG (قاعدة معرفة) | ~7,300 مفهوم / ~19,000 علاقة | ✅ حي، أساسي | `knowledge/cognitive_graph.json` |
| NeuralCore | ~640K باراميتر | ✅ حي، متصل بالإجابة | `ai/neural_core.py` |
| ArabicTransformer | ~40M باراميتر | ✅ حي، مدرَّب عصر واحد على CKG | `ai/arabic_transformer.py` |
| ReasoningPipeline | — | ✅ نقطة الدمج الرئيسية | `ai/reasoning_pipeline.py` |
| DeepRoutingNetwork | ~640K | ⚠️ مبني لكن **غير متصل** بالإجابة الحية | `ai/deep_routing_network.py` |
| DynamicWeightLayer | متغير | ⚠️ مبني لكن **غير متصل** بالإجابة الحية | `ai/dynamic_weight_layer.py` |
| NeuralWeightLayer | 784×784 | ⚠️ مبني لكن **غير متصل** بالإجابة الحية | `ai/neural_weights.py` |
| DeepCirculantPyramid | ~14.1M | 🧪 بحث معماري، غير مُفعّل | `ai/multimodal_network.py` |
| LoRA Adapters | — | 🧪 جاهزة للاستخدام مستقبلاً | `ai/lora_adapter.py` |

**ملاحظة صريحة:** `DeepRoutingNetwork` و`DynamicWeightLayer` و`NeuralWeightLayer`
الثلاثة بيعملوا نفس الوظيفة تقريباً (شبكة توجيه قرار) بمنطق نمو مختلف لكل
واحدة، ومتصلين بس بمسار قديم منفصل (`QuranContinuousTrainer` →
`KnowledgeTrainer`) **غير مستخدم في التطبيق الحي حالياً**. تم إصلاح باغ
حقيقي فيهم (`DeepRoutingNetwork.load()` كان بيقبل أبعاد قديمة غير متوافقة
بصمت) لكن التوحيد الكامل لسه مؤجل (خطر أعلى من الفايدة حالياً لأنهم كود
غير مستخدم).

### منظومة الوكلاء (تبويب 🤖 الوكلاء)

- **🎯 الوكيل الموحّد** — واجهة محادثة واحدة مستمرة، توجّه كل رسالة تلقائياً
  خلف الكواليس لأنسب فئة متخصصة من الفئات الثمانية أدناه.
- **🤖 وكلاء AI** — 8 فئات وكلاء متخصصة مستقلة، كل واحدة بذاكرة محادثة معزولة
  وإمكانية بحث ويب حقيقي اختيارية (DuckDuckGo، عبر flag `web_enabled` لكل وكيل):

  | الفئة | التخصص |
  |---|---|
  | المساعد الشخصي | تنظيم مهام، جدولة، صياغة رسائل، متابعة يومية |
  | أتمتة العمليات | تصميم سير عمل (workflows) وأتمتة مهام متكررة |
  | تحليل البيانات | قراءة أرقام، مؤشرات حديثة من الويب، رؤى قابلة للتنفيذ |
  | التفكير والاستدلال | تحليل منطقي، مقارنات، حل مشكلات خطوة بخطوة |
  | وكيل البرمجة | مراجعة أكواد، حلول تقنية، شرح مفاهيم برمجية |
  | وكيل البحث | بحث ويب حقيقي (DuckDuckGo)، تلخيص، إجابات بمصادر فعلية |
  | الصيانة الذاتية | يفحص ملفات المشروع، يكتشف أخطاء محتملة، يقترح تصحيحات |
  | صناعة المحتوى | يكتشف مواضيع رائجة (Google Trends RSS)، يكتب مقالات SEO، يجدول نشرها |

- **🤝 منسّق الوكلاء** — يوجّه مهمة/سؤال المستخدم تلقائياً لوكيل أو أكثر من
  الفئات الثمانية أعلاه (نفس الجلسات وذاكرة المحادثة)، بدعم وضع تسلسلي.
- **🐝 السرب الذكي** — واجهة لنظام الوكلاء الوظيفي (`ai/agent_factory.py`).

كل تفاعلات هذي الفئات تُسجَّل بسجل تدقيق (`ai/agent_audit.py`،
`memory/agent_audit.db`) لأغراض الرقابة التشغيلية (أي فئة استُدعيت، من أين،
هل استُخدم بحث ويب فعلي، أي مزوّد LLM أجاب).

### مزوّدو LLM (سلسلة الاحتياط `LLMFallback`)

الترتيب: Anthropic (الأولوية الأولى) → Cloudflare Workers AI (مجاني، يعمل
من اليمن) → Gemini → OpenRouter → OpenAI → Together → Groq → HuggingFace
(Falcon-Arabic-7B) → نموذج محلي عبر Ollama (للنشر المغلق) → **CKG
Synthesis** (احتياطي أخير محلي بالكامل، بدون أي مزوّد خارجي — يضمن أن
النظام يجاوب دائماً حتى بدون أي مفتاح API).

## التشغيل

```bash
pip install -r requirements.txt
streamlit run streamlit_app.py --server.port 5000
```

خادم API اختياري منفصل (غير مربوط بواجهة Streamlit):

```bash
python api_server.py   # FastAPI، لمحرك core.engine
```

**نشر داخل شبكة مغلقة بدون إنترنت خارجي (نموذج محلي عبر Ollama):** انظر
[`OFFLINE_DEPLOYMENT.md`](OFFLINE_DEPLOYMENT.md).

## التخزين الدائم

- `memory/nsm_context.db` — سجل المحادثات (SQLite)
- `data/artifacts.db` — الواجهات التفاعلية المحفوظة + إعدادات المستخدم
- `data/mesh.db` — محرك Node/Engine
- `models/transformer_ckg_v1/` — أوزان `ArabicTransformer` المدرَّبة (~305MB)

⚠️ **تنبيه حجم:** مجلد الأوزان كبير (~305MB) ومخزّن كـ blobs عادية في Git
(مش LFS — LFS اتجرّب وفشل بسبب قيود شبكة في بيئة التطوير المستخدمة، ممكن
تتفعّل لاحقاً من جهاز بوصول كامل للإنترنت: `git lfs track "*.npy"`).

## حالة الجاهزية للإنتاج/البيع

**غير جاهز بالكامل بعد.** نواقص معروفة:
- كود مكرر غير مستخدم (الجدول أعلاه) يحتاج قرار نهائي (حذف/تفعيل/توحيد).
- `ArabicTransformer` مدرَّب عصر واحد بس على بيانات CKG صناعية (قوالب
  محدودة) — الفهم الدلالي محدود، مش مقصود يكون مصدر حقائق.
- بدون test suite آلي شامل — ملفات `test_*.py` موجودة بمكوّنات متفرقة
  (`ai/test_neural_core.py`، `knowledge/test_qa_engine.py`، إلخ) بدون تغطية
  كاملة، رغم إن CI مُفعّل فعلياً (`.github/workflows/tests.yml`) ويشغّل
  pytest + فحص py_compile على كل push/PR.
- `streamlit_app.py` لا يزال ملفاً واحداً (~9,800 سطر) — التقسيم لوحدات
  أصغر مؤجَّل حالياً (خطر التعديل الجذري > الفائدة الفورية).
- بعض الميزات (WhatsApp integration، نظام حسابات المستخدمين) تحت التطوير.
- ✅ **مُصلَح:** ثغرة تسريب مفتاح OpenRouter API عبر HTML (كان يُحقَن
  بنص صريح داخل خاصية `value` لحقل `type="password"`).
