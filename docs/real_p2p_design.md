# تصميم بروتوكول التواصل الحقيقي (Real P2P Communication Design)

## 1. المفهوم العام
يهدف هذا التصوير إلى تحويل العقد من مجرد سجلات في ملف JSON إلى **خوادم نشطة** تتحدث مع بعضها البعض عبر شبكة TCP. سيتم استخدام مكتبة `asyncio` في Python لضمان المعالجة غير المتزامنة لآلاف الرسائل.

## 2. المعمارية التقنية

### أ. خادم الاستماع (Node Listener)
كل عقدة ستقوم بفتح منفذ (Port) خاص بها للاستماع للخبرات القادمة.
*   **البروتوكول**: TCP (أو WebSockets لاحقاً).
*   **تنسيق البيانات**: JSON مشفر.

### ب. عميل الإرسال (Node Client)
عندما تريد العقدة مشاركة خبرة، ستقوم بالاتصال المباشر بعنوان الـ IP والمنفذ الخاص بالعقدة المستهدفة.

## 3. تدفق البيانات (Data Flow)
1.  **اكتشاف الأقران (Discovery)**: العقدة تقرأ قائمة الأقران وعناوينهم من `network_state.json`.
2.  **المصافحة (Handshake)**: العقدة "أ" تتصل بالعقدة "ب" وتؤكد هويتها الرقمية.
3.  **تبادل الخبرات (Experience Exchange)**: إرسال بيانات الخبرة (kind, data, timestamp).
4.  **تحديث الأوزان (Weight Sync)**: العقدة المستلمة تقوم بتحديث أوزانها السلوكية فوراً.

## 4. المزايا المتوقعة
*   **السرعة**: تواصل لحظي دون الحاجة لانتظار دورة كتابة الملف.
*   **الاستقلالية**: إذا تعطل الخادم المركزي، تستمر العقد في التحدث مع بعضها البعض.
*   **الواقعية**: محاكاة حقيقية لبيئة الإنتاج الموزعة.

## 5. حالة التنفيذ الفعلية وقياسات الأداء (مُحدَّث)

هذا التصميم **منفَّذ فعلياً وليس مجرد خطة** — `ai/living_mesh.py` (WebSocket
حقيقي عبر aiohttp، توقيع/تحقق RSA، اكتشاف لامركزي متعدد القفزات) و
`ai/gradient_mesh.py` (تبادل تدرجات P2P موقّع فوق نفس الطبقة). القياسات
التالية أُخذت فعلياً بتشغيل 3 عقد حقيقية، كل واحدة بعملية نظام تشغيل
منفصلة تماماً بمنفذ ومجلد بيانات (`data_dir`) معزولين — لا محاكاة بنفس
العملية — عبر `tests/test_real_p2p.py` و`tests/test_gradient_mesh_dedup.py`.

| المقياس | القيمة المقيسة فعلياً | ملاحظات |
| :--- | :--- | :--- |
| زمن اكتشاف قرين مباشر (peer discovery) | 12–27 ms | اتصال محلي (loopback)؛ يشمل بناء الرسالة الموقّعة + جولة WebSocket كاملة |
| اكتشاف متعدد القفزات (Multi-hop) | ~12 ms إضافية | عقدة ثالثة تتعرف على عقدة لم تتصل بها مباشرة، عبر عقدة وسيطة فقط |
| بث تدرجات (broadcast) لقرينين (~30KB) | 24–42 ms لكل جولة | يشمل التسلسل (serialization ~1ms) + إرسال WebSocket موقّع مباشر لكل قرين |
| Throughput (بث متتالي) | ~29.5 بث/ثانية | بحمل تجريبي صغير (نموذج torch بسيط)؛ رقم توضيحي لا يعكس شبكات إنتاجية حقيقية |
| نجاح تسليم فردي | 24/25 (96%) | فشل اتصال عابر واحد لوحظ أثناء القياس، لم يتكرر بجولات لاحقة |

**ملاحظة مهمة اكتُشفت أثناء القياس (وتم إصلاحها):** آلية الترحيل المحدود
(`hops < 3`) لرسائل `gradient_push` كانت تُضخِّم عدد النسخ المستلمة فعلياً
(٥ بث → ١٣ استقبال) بسبب غياب معرّف `_gossip_id` ثابت يُفعِّل آلية منع
التكرار الموجودة أصلاً بالنظام. تم إصلاحه (كل بث يصل الآن مرة واحدة بالضبط
لكل قرين) — التفاصيل في سجل الـcommits `e06f88b` و`d63b208` و`0d276a0`.

هذه الأرقام قياسات محلية (loopback) لغرض التحقق الوظيفي والانحدار، وليست
اختبار حِمل أو زمن استجابة عبر شبكة إنتاجية حقيقية (WAN) — أي رقم أداء
لبيئة إنتاج فعلية يحتاج قياساً منفصلاً بعقد على أجهزة/شبكات مختلفة فعلياً.
